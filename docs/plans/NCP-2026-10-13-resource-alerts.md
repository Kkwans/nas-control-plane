# M15：可选资源告警首切片（已评审，分片实施中）

日期：2026-10-13。源码调查基线：`53962e4541d0812266afd2fe6ed566f82ff11a13`。方案阶段仅新增文档；随后已完成纯状态机及 Collector/API 接线和隔离验证，前端与完整 CI/视觉验收仍在推进，见第 6 节。没有运行真实采集、访问Docker/NAS/socket或打开浏览器。遵循 AGENTS.md、roadmap 的 M15 容量/保留/失败边界，以及前后端审计中“不把缺失当健康”的要求。

## 1. 决策：两条固定规则，复用现有采集 owner

本片只做 **CPU 与内存持续高使用率的控制台提示**。默认关闭，已新增 Server 启动参数 `--resource-alerts` 才启用；不修改现有部署配置，也不在本片运行服务或启用真实环境。规则固定、只读展示，不提供规则编辑器、通知发送或自动修复。入口放在现有“系统监控”页，不增加一级导航。

优点：无需新调度器、数据库表或服务；无页面也能评估；多标签只读同一结果。代价：需要日后明确授权的配置/部署才能实际启用，告警不跨 Server 重启保存。这是可选的当前运行期提示，不是可靠告警投递系统。

### 已核对的代码事实

- `internal/monitoring/collector.go` 的 `Collector.Run/step` 已独立每 5 秒采样，显式 `Clock`、5 秒源预算、2 秒 SQL 预算、深复制 `Latest`、取消与 `Done` 均可复用。`cmd/ncp-server/main.go:runHTTPServer` 已拥有该生命周期。
- `validateSummary` 先检查时间递增、15 秒年龄、5 秒未来容差和 1 MiB 编码预算。它不保证 CPU/内存字段合法；`historySample` 另外检查字段及 warning。告警必须独立做逐规则有效性校验，不能看到 nil error 就判定健康。
- `internal/system/summary.go` 提供 `CPU.UsagePercent`、`Memory.TotalBytes/UsedBytes` 和按源 warning。`internal/system/monitoring.go` 的磁盘百分比是全部挂载点合计，可能掩盖单个挂载点满盘。
- `internal/controlstore/metrics.go` 保存每分钟第一个完整样本，保留 7 天；不是一分钟平均或最大值。`frontend/src/domain/monitoring/series.ts` 已明确缺口、计数器重置等语义。
- `internal/httpapi/realtime.go` 以数据时间和接收时间双年龄判断新鲜度；SSE 的外层时间/心跳不能刷新数据。现有历史页 `MonitoringView.vue` 独立读取历史，不能把其最新一分钟点当当前健康。
- `internal/dockerrealtime/events.go` 是 Docker 清单失效/对账信号，按需求运行；不是通用告警总线或可靠事件日志，本片不接入它。

**不采用“重读最近历史再推算持续超限”**：每分钟首点无法证明这一分钟始终超限，还会把持久化失败混成资源状态。历史只作背景趋势；不得回放生成当前告警、重启补发或伪造持续时间。

## 2. 固定规则与精确状态语义

以下数值是可评审的首版产品默认值，不是经过实际 NAS 校准的安全界限：

| 规则 | 触发 | 恢复 | 展示 |
|---|---|---|---|
| `host.cpu.high` | CPU ≥90%，合格观察连续覆盖 ≥120 秒 | CPU ≤80%，合格观察连续覆盖 ≥60 秒 | CPU 持续高使用率 |
| `host.memory.high` | 已用/总内存 ≥90%，合格观察连续覆盖 ≥120 秒 | 已用/总内存 ≤85%，合格观察连续覆盖 ≥60 秒 | 内存持续高使用率 |

均为 warning，不新增 critical 等级。说明“按约 5 秒采样判断，采样间的变化不可知”；不称连续测量、故障证明或 NAS 整体健康证明。

- 两个维度分开：`condition = normal | pending | firing | recovering`；`availability = fresh | unknown | stale`。另有整个功能的 `enabled=false`。冷启动无样本为 unknown，不输出“正常”。
- 一个新、合法、时间递增的样本最多评估一次。用服务接收的单调经过时间累计，源 `CollectedAt` 负责身份和年龄校验；重复 SSE/GET/历史点不累计。触发/恢复只能由新的合格样本确认，页面时间推进不能触发。
- 120 秒从首个 ≥触发阈值的样本开始，不将第一个样本算作已经经过 5 秒。pending 遇到低于触发阈值立即重置；未触发时，滞回区间也不会累计触发时间。
- firing 后仅 ≤恢复阈值开始 recovering；处于滞回区间保持 firing。recovering 遇到 >恢复阈值回 firing 并清恢复计时。满 60 秒的合格恢复观察才回 normal，并记录最后恢复时间。一个持续事件只触发一次，不每 tick 重开。
- 相邻合格样本的接收或数据时间间隔 >15 秒，任何源 RPC 失败、无效/重复/倒退时间戳，均打断连续性。清 pending/recovering 计时；已 firing 的事件保留“尚未确认恢复”，不得因失联自动恢复。新鲜数据回来后重新积累完整恢复时长。
- CPU warning 或 CPU 非有限/不在 0–100 范围，仅使 CPU 规则 unknown；内存 warning、总量为零或 used>total，仅使内存规则 unknown。其他源 warning 不抹掉合法 CPU/内存观察。全快照时间/编码校验失败则两条均 unknown。
- 最后合法数据或其接收时间年龄 >15 秒为 stale；明确失败/字段无效优先显示 unknown，附稳定原因码。两者均用中性色文案，不能显示绿色“正常”。保留最后值必须同时展示“上次有效值”和原时间。
- 服务时钟异常/后退重置连续性并显示 unknown；恢复后重新计时，不修系统时钟。实现应保留 `time.Time` 的单调部分，不将运行计时先序列化成 UTC 再计算；fake clock 需要覆盖异常路径。
- Server 重启：两个规则与事件全部从 unknown 重建，不恢复旧计时，不将进程结束记为资源恢复。关闭功能是 disabled，不是 resolved。首片没有运行中规则变更、手动重置、静音或确认操作。

## 3. 最小实现边界与预算

### 后端

1. 在 `internal/monitoring` 新增小型纯状态机（如 `alerts.go`）；由现有 `step` 在源校验后、SQL 写入前同步消费本轮成功/失败。不要给 HTTP/SSE 添加评估副作用。不要新增 tick/goroutine、Job、队列、RPC 或宿主机读取。
2. `Options` 增加默认 false 的开关，main 原有 flag 解析向下传递。快照通过 collector 锁一次性发布；读取返回独立值，避免“新样本配旧规则状态”。原 summary/history API 语义不变。
3. 新增受现有认证保护的只读 `GET /api/v1/monitoring/alerts`，provider 只读内存；不调用源、不读 SQL。同步 OpenAPI 和前端运行时响应解析。首片不修改 SSE envelope，避免拓宽共享实时契约。
4. 响应包含 `enabled`、`observedAt`（响应时间）、`startedAt`（本次 evaluator 启动时间）及两条规则：固定 id/阈值/时长、condition、availability、reasonCode、最近合格 `sampleAt/receivedAt/value`、pending/firing/recovering 起点、可选最近恢复时间。时间和值未取得时显式 nullable，不能填 0。响应时间不保鲜样本。
5. provider 缺失/停止应返回稳定 503 `MONITORING_ALERTS_UNAVAILABLE`；配置关闭正常返回 enabled=false。字段无效/源断开属于正常 200 的 unknown/stale，不能将正常“暂不可评估”伪装 HTTP 故障；缺少必须字段的成功响应由前端整份拒绝。

### 资源与保留

- 固定两条规则、每条一个当前事件和计时状态；只保存每条最近一次恢复时间，满 24 小时不再输出，或下次恢复替换。没有事件数组、事件积压、通知重试、自由输入名称或动态规则数。
- 当前未确认恢复的 firing 不因 24 小时到期而清除；可无限持续但只占固定状态。重启全部丢失，并在 UI 固定说明“仅本次 Server 运行期”。这里的保留是内存语义，不是持久告警历史。
- 每次已有采集只进行两次常数级判断；0 次新增源 RPC、SQL 写或历史查询。HTTP 返回 ≤8 KiB 的固定响应预算；超过预算显式错误，不截断声称完整。正常每标签最多一个 5 秒轮询、一个在途请求；多个标签不增加采样。
- 读取时以传入 now 投影 stale/24 小时过期展示，不变更判定状态、推进持续计时或写事件。下一次 step 必须依据间隔重新判断连续性，不能因没客户端读取而漏掉过期。
- 不增加每样本日志；状态变化也不作为耐久审计证据。沿用采集器已有源/持久化错误诊断；SQLite 故障不阻止合法实时告警评估，也不能被告警“正常”隐藏。

### UI

监控页顶部新增独立 `ResourceAlertsPanel`：两个规则、当前值/最后有效时间、规则说明和状态。与历史图表分开加载/重试；更改历史范围不会重置当前规则。文案明确“当前资源提示”，避免用户以为在评估所选历史范围。

- 独立呈现 disabled、首次加载、正常、等待持续确认、已触发、恢复观察、unknown/stale、读取失败、旧结果刷新失败。正常只称“未达到本规则告警条件”，不称 NAS 健康。
- 中断期间原 firing 显示“此前已触发，数据不可用，恢复尚未确认”；不从警告列表消失，也不把旧值画成当前红色读数。
- 用现有 ResourceState/StatusPill/设计 token，文本与图标不只靠颜色；仅真正状态变化使用 polite live region，不每 5 秒播报值或倒计时。无 toast 风暴、声音、桌面推送或新全局红点。
- 轮询采用完成后再安排下一次读取，无重叠；卸载/退出/认证代次变化取消 controller 和 timer，旧响应不得覆盖新会话。页面隐藏时暂停，恢复可见立即只读刷新。独立本地新鲜度检查让网络停滞时旧结果及时变 stale；收到新的响应时间不解除 stale。
- 手动重试仅 GET，不修改状态机。当前告警和历史错误独立显示；历史本身不会补点，不能提供精确事故回放。320/390/768/1440 与 200% 根字号需实际 fixture 像素检查后才称 UI 验收。

## 4. 隔离验收清单

以下保留原计划的完整验收清单。后端已取得的证据见第 6 节；未列为通过的前端、浏览器与像素项目仍待验收。验证仅使用 fake source/store/clock、HTTP recorder 和前端 fixtures，禁止真实 host/Docker/NAS/socket。

1. 精确边界：阈值等于/略小于，119.999/120 秒触发，59.999/60 秒恢复；首点不偷加间隔，CPU/内存两条独立。
2. pending 中断、滞回带、恢复中反弹、长事件无重复触发、恢复后重新超限产生新事件；重复/乱序/未来/零时间与时间后退。
3. 15 秒恰好与超过的双年龄边界、两点间 >15 秒打断、RPC 失败立即 unknown、没有新样本绝不按墙钟触发/恢复；已触发后失联保持未确认恢复。
4. CPU/内存 warning 与坏数、NaN/Inf、零内存/越界内存、其他源失败、历史写失败/清理失败均验证正确隔离；合法零 CPU 可用，缺失不能变零。
5. 零页面继续评估；100 次 GET 不增加 source/SQL 次数、不累计时间；快照并发读深复制/race；停止和 disabled、重启冷态、最近恢复时间 24 小时到期而活动事件不被清除。
6. API 认证、disabled/unknown/stale/firing、缺 provider、全部枚举/nullable/8 KiB 边界、坏成功响应；前端 A 慢 B 快、卸载/登出后迟到、旧 finally、慢轮询无并发、隐藏恢复和假时钟 stale。
7. fixture UI 覆盖上述所有状态和独立历史失败；键盘、屏幕阅读语义、长时间文本、窄屏及减少动态效果。浏览器实际执行与像素证据作为后续明确步骤，本计划不运行浏览器。

实施顺序：先评审规则与只读/易失边界，再做纯状态机及 fake-clock 测试，再接既有 collector + API +契约，最后独立 UI/fixtures 与静态构建。只运行精确 fake 测试，不能顺手执行带真实 provider 的集成测试；Go 编译、前端类型/lint/build 与实际浏览器验证分别报告。

## 5. 明确不做

外部邮件/Webhook/短信/推送、供应商/凭据、生产启用或部署；任意规则表达式、规则 CRUD、全局设置写入、分级升级、告警确认/静音/值班/投递保证、跨重启告警历史、历史补算、自动重启/清理等修复行为；单挂载点容量/温度/网络速率/Docker 容器存活告警。磁盘告警需先有稳定挂载身份与逐挂载语义，温度需明确传感器缺失/设备特定阈值；不能把当前合计磁盘百分比包装为可靠满盘预警。

本片完成仅表示固定 CPU/内存规则在既有采集链路上可解释、可取消、有界，并能在控制台区分当前状态与未知。不会完成整个 M15，也不证明实际 NAS 可用性、容量阈值适合用户或生产已启用。


## 6. 2026-10-13 实施与验证记录

### 后端已实现

- `internal/monitoring/alerts.go` 实现固定 CPU/内存规则的不可变纯状态机；逐规则有效性、双时间年龄、连续性中断、触发/恢复边界、最近恢复时间保留和只读投影均有隔离测试。
