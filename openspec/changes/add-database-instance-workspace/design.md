## Context

NCP 当前通过 Root Agent 的 Docker Engine 清单提供容器与 Compose 项目事实，数据库导航仍为不可进入的占位项。NAS 实机已存在 MySQL 和 Valkey 容器，但本阶段不应引入数据库凭据、网络探测或数据读写。真实浏览器验收还发现登录后首次快照和 SSE 持续采样不够可靠，需要在同一阶段先补齐数据刷新闭环。

## Goals / Non-Goals

**Goals:**

- 从现有 Docker 清单稳定识别常见数据库实例并返回可解释的只读元数据。
- 提供与现有控制台设计语言一致的数据库工作区、详情和移动端体验。
- 确保登录后立即加载数据，并在 SSE 没有产生可见事件时仍保持周期更新。
- 保持 Root Agent、Server、Vue 三层边界和单一事实源。

**Non-Goals:**

- 不连接数据库，不验证账号，不列出库、表、键、用户或权限。
- 不启动、停止、重启数据库容器，不执行备份、恢复、SQL 或配置修改。
- 不扫描宿主机端口，不读取容器环境变量或秘密文件。
- 不引入数据库驱动或新的外部依赖。

## Decisions

### 1. 在 Server 侧从 Agent Docker 清单派生数据库实例

Root Agent 继续负责读取 Docker Engine；Server 使用纯分类器把 `docker.Inventory` 转换为数据库实例响应。相比新增数据库 RPC，这种方式复用现有强类型链路，不增加 Socket 协议和部署耦合，同时仍以 Root Agent 返回的 Docker 事实为来源。

分类优先使用镜像仓库名称，其次使用 Compose service 和容器名称。首批识别 MySQL、MariaDB、PostgreSQL、Redis 与 Valkey，未知镜像不猜测为数据库。

### 2. 扩展 Docker 容器模型返回挂载摘要

现有 Docker 清单新增 `mounts` 字段，仅包含挂载类型、源、目标和读写状态，不返回环境变量、驱动选项或秘密内容。数据库详情据此展示数据目录位置；现有前端对新增字段保持兼容。

### 3. 数据库 API 保持只读且受现有 Root 会话保护

新增 `GET /api/v1/databases/instances`，响应包含采集时间、实例数组和类型汇总。实例包含稳定容器 ID、名称、引擎、镜像、状态、项目、服务、端口、创建时间与挂载。接口复用统一错误码和 Agent 超时。

### 4. 数据库页面采用密集主列表与详情抽屉

桌面端用表格比较实例类型、状态、镜像、端口、项目和数据目录；手机端转换为无横向滚动的实例卡片。详情抽屉展示完整端口和挂载，不提供虚假的连接、备份或控制按钮。

### 5. SSE 与周期刷新组成双保险

`startRealtime()` 自身立即触发一次刷新，避免登录组件切换时首次请求丢失。登录期间保持 SSE，同时固定每 5 秒执行一次可见页面刷新；现有 `refreshPromise` 合并同一时刻的重复请求。这样即使代理或浏览器只报告连接成功却没有分发事件，图表仍持续获得真实样本。

## Risks / Trade-offs

- [镜像名称分类可能漏掉定制数据库镜像] → 只识别明确模式，未知实例不展示，后续增加用户标注能力。
- [完整宿主机挂载路径会增加页面信息密度] → 主列表仅显示首个数据挂载，完整列表放入详情抽屉。
- [SSE 与 5 秒刷新可能同时触发] → 复用单一 `refreshPromise` 合并并发，不引入请求队列。
- [当前阶段无法证明数据库可连接] → 页面明确标注“容器发现”，不显示连接健康或数据库内部指标。

## Migration Plan

1. 先部署兼容新增字段的 Server 与前端，再按现有方式增量重建 NCP Server/Console。
2. 不修改 Root Agent systemd 配置、Docker 数据库容器或任何数据卷。
3. 验证 API 只返回实例元数据、首页样本持续增长、数据库页面在桌面和手机布局可用。
4. 回滚时恢复上一版 NCP 镜像和前端产物；数据库实例与数据卷不受影响。

## Open Questions

- 自定义数据库镜像的人工标注与连接配置留到后续规格。
- 数据库内部版本、库表、备份与慢查询需要独立变更，并在引入凭据模型后再设计。
